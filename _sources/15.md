# Infrastructure Algorithms

Infrastructure algorithms apply familiar data structures to systems that handle requests, caches, queues, and distributed state. Their production implementations usually rely on a shared store such as Redis so that every server sees the same data.

## Rate Limiting

A rate limiter restricts how often a client may perform an action. For example, an API may allow at most `100` requests per user every `60` seconds.

Every rate limiter needs:

- a **key**, such as a user ID, API key, or IP address;
- a **limit**, which is the maximum number of requests;
- a **window size**, which defines the time interval;
- a decision for each request: allow or reject.

The algorithms below accept timestamps as seconds and return `True` when a request is allowed.

### Fixed Window Counter With a Key-Value Store

A fixed-window limiter divides time into non-overlapping windows. For a window size of `60` seconds:

- timestamps `0` through `59` belong to window `0`;
- timestamps `60` through `119` belong to window `1`;
- timestamps `120` through `179` belong to window `2`.

Compute the current window with integer division:

```text
window_id = timestamp // window_size
```

The key combines the client and the window. A request at a later timestamp automatically uses a new key when the division produces a new `window_id`.

The following dictionary class models the small part of a key-value store that the rate limiter needs:

```{code-block} python
---
linenos:
---
class DictKeyValueStore:
    def __init__(self):
        self.values = {}
        self.expires_at = {}

    def remove_expired(self, timestamp):
        expired = [
            key
            for key, expiry in self.expires_at.items()
            if expiry <= timestamp
        ]
        for key in expired:
            del self.values[key]
            del self.expires_at[key]

    def increment(self, key):
        self.values[key] = self.values.get(key, 0) + 1
        return self.values[key]

    def expire_at(self, key, timestamp):
        self.expires_at[key] = timestamp
```

The rate limiter increments the current key and adds an expiration only when the counter becomes `1`. That means the TTL is created once, with the key, rather than being extended by every request.

```{code-block} python
---
linenos:
---
class FixedWindowRateLimiter:
    def __init__(self, limit, window_size, store=None):
        self.limit = limit
        self.window_size = window_size
        self.store = store or DictKeyValueStore()

    def allow(self, client_id, timestamp):
        self.store.remove_expired(timestamp)

        window_id = timestamp // self.window_size
        key = (client_id, window_id)
        count = self.store.increment(key)

        if count == 1:
            window_end = (window_id + 1) * self.window_size
            self.store.expire_at(key, window_end)

        return count <= self.limit
```

Example:

```{code-block} python
limiter = FixedWindowRateLimiter(limit=3, window_size=10)

limiter.allow("user-1", 1)   # True: count is 1 in window 0
limiter.allow("user-1", 4)   # True: count is 2 in window 0
limiter.allow("user-1", 8)   # True: count is 3 in window 0
limiter.allow("user-1", 9)   # False: count is 4 in window 0
limiter.allow("user-1", 10)  # True: window 1 uses a new key
```

With Redis, the important operations are `INCR key` followed by `EXPIREAT key window_end` only when `INCR` returns `1`. Those operations should be performed atomically with a transaction or Lua script.

#### Complexity and Tradeoff

The rate-limit decision takes `O(1)` average time in a real key-value store. The dictionary example scans expired keys only to simulate Redis's automatic TTL cleanup.

Fixed windows are simple and memory-efficient, but they allow bursts at boundaries. With a limit of `100` per minute, a client could send `100` requests just before a minute ends and another `100` immediately after the next minute begins.

### Sliding Window Log With a Sorted Set

A sliding-window limiter avoids the fixed-window boundary burst. For every request at time `now`, it counts only requests in the exact interval `(now - window_size, now]`.

A Redis sorted set is a natural fit:

- the **score** is the request timestamp;
- the **member** is a unique request ID;
- entries are kept sorted by timestamp.

Python does not include a built-in sorted set. The example below uses a sorted list of `(timestamp, request_id)` tuples to model the same operations. `bisect_right` finds all expired entries, while `insort` adds the new request in sorted order.

```{code-block} python
---
linenos:
---
from bisect import bisect_right, insort


class SlidingWindowRateLimiter:
    def __init__(self, limit, window_size):
        self.limit = limit
        self.window_size = window_size
        self.requests = {}
        self.next_request_id = 0

    def allow(self, client_id, timestamp):
        events = self.requests.setdefault(client_id, [])
        cutoff = timestamp - self.window_size

        # Redis: ZREMRANGEBYSCORE key -inf cutoff
        first_active = bisect_right(events, (cutoff, float("inf")))
        del events[:first_active]

        # Redis: ZCARD key
        if len(events) >= self.limit:
            return False

        # Redis sorted-set members must be unique.
        self.next_request_id += 1
        event = (timestamp, self.next_request_id)

        # Redis: ZADD key timestamp request_id
        insort(events, event)
        return True
```

Example:

```{code-block} python
limiter = SlidingWindowRateLimiter(limit=3, window_size=10)

limiter.allow("user-1", 0)   # True: active timestamps are [0]
limiter.allow("user-1", 1)   # True: active timestamps are [0, 1]
limiter.allow("user-1", 9)   # True: active timestamps are [0, 1, 9]
limiter.allow("user-1", 9.5) # False: three requests are still active
limiter.allow("user-1", 10)  # True: timestamp 0 has expired
```

In Redis, run `ZREMRANGEBYSCORE`, `ZCARD`, and the conditional `ZADD` atomically. Set a TTL on the sorted-set key as cleanup for clients that stop sending requests.

#### Complexity and Tradeoff

For `n` active requests, Redis sorted-set insertion and removal cost `O(log n)` per element, and counting costs `O(1)`. The Python list stand-in has `O(n)` insertion and deletion because list elements may need to shift.

The sliding-window log is more accurate than a fixed window, but it stores one entry per allowed request. A high-volume system may prefer a sliding-window counter or token bucket when lower memory usage matters more than exact timestamps.

### Choosing Between Them

| Algorithm | Accuracy | Stored data | Main advantage | Main drawback |
| --- | --- | --- | --- | --- |
| Fixed window counter | Approximate near boundaries | One counter per active window | Simple and inexpensive | Allows boundary bursts |
| Sliding window log | Exact | One timestamp per allowed request | Smooth, precise enforcement | Uses more memory |

### Production Considerations

1. Keep the update and limit check atomic so concurrent servers cannot admit too many requests.
2. Use a shared clock or server-side time when clock differences between application servers matter.
3. Apply TTLs so inactive clients do not leave permanent keys behind.
4. Decide whether rejected requests should count toward the limit. The sorted-set implementation above records only allowed requests; the fixed-window counter counts every attempt.
5. Return useful metadata such as the remaining request count and when the client may retry.
